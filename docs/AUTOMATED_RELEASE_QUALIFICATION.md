# Automated native-Termux release qualification

The ordinary automated release qualification class is
`official_termux_native_automated_v1`. It replaces an operator-entered
60-minute observation with closed, machine-verifiable evidence that is
generated by a separate first-attempt `workflow_run` qualifier after the first
successful attempt of the exact `main` Android workflow.
It does not convert emulation time into physical time and does not claim that a
container is a phone.

The qualifier checks out only the repository and commit that define its trusted
workflow (`job.workflow_repository` at `job.workflow_sha`). Before it consumes
any checked-out helper or artifact, it requires that immutable workflow commit
to equal the completed Android run's exact `main` head SHA.

Automated release qualification proves the exact artifacts under the digest-pinned official Termux userland on native ARM64, including deterministic Android-provider simulation and isolated deployment recovery. It does not certify physical-device, OEM, battery-aging, thermal-soak, radio, Doze, or Android-framework behavior.

## Evidence boundary

Every release-eligible automated qualification envelope, staging manifest, and
retained attachment or draft-verification identity record carries this exact
closed boundary:

```json
{
  "physicalDeviceObserved": false,
  "androidFrameworkObserved": false,
  "sustainedPhysicalSoak": false,
  "physicalCertification": "not_run"
}
```

Automated records contain no physical minutes, equivalent minutes, accelerated
minutes, time-dilation claim, or inferred physical certification. Optional
physical qualification remains available through
`scripts/package_physical_qualification.sh`, but it is a separate evidence tier
and cannot be submitted as the automated class.

## Qualification chain

One release-eligible envelope binds all of the following to the same commit and
version:

1. First-attempt successful `main` push runs for CI, Security, and Android,
   plus the separate first-attempt post-run qualifier that consumes them.
2. All seven Android AArch64 binaries and their exact workflow manifests.
3. Aggregate schema/gate v4 evidence from the digest-pinned official Termux
   userland on a native ARM64 runner.
4. Battery, volume-status, volume-control, and command provider boundary
   reports.
5. Classifier v3 route `automated_release_qualification`.
6. The exact six committed deployment scenarios: isolated fresh deployment,
   failed-upgrade recovery, supervised restart, rollback recovery, uninstall,
   and bounded cleanup.
7. The committed qualification policy and its SHA-256 digest.
8. The pinned Termux registry manifest digest, materialized base-image ID,
   separately derived runtime-image ID, plus Android/Bionic linker identity,
   digest, and byte size.
9. A retained content-addressed runtime archive, exact package lock, snapshot,
   and offline replay record. The replay verifies the archive digest, one-image
   layout, loaded image ID, platform, the exact non-root runtime user
   `1000:1000`, rootfs layers, package inputs and indexes, installed-package
   inventory, required commands, and Android linker with
   `runtimeNetworkAccess:false`.

The aggregate, specialized, classifier, and deployment reports are components;
none grants release eligibility alone. Only
`scripts/package_automated_qualification.sh` can emit the closed
`automated-qualification-v1.json` envelope with `releaseEligible:true`, after
all identities and policy digests reconcile.

The Android workflow emits exactly nine artifacts: seven posture bundles, one
seven-report component artifact, and one three-file retained-runtime snapshot
artifact. The read-only `Automated Release Qualification` workflow checks out the triggering
Android commit, re-resolves the exact Android, CI, and Security runs and exact
artifact IDs/digests, invokes the canonical assembler, freezes the resulting
12-member evidence set (seven components, four retained-runtime members, and
the envelope), re-queries every upstream identity, and only then
uploads `termux-mcp-native-qualification-evidence`. Android therefore cannot
declare its own run release-eligible.

The official base image is pinned by registry manifest digest. The workflow
also records the local Docker config/image ID materialized from that manifest,
builds a derived image containing `file`, `jq`, `python` (including `python3`),
and `termux-services`, requires its local image ID to differ from the base image
ID, declares and observes UID/GID `1000:1000` for both the offline package build
and runtime execution, and executes the image by its exact ID. This is a
container-user requirement, not an Android UID, physical-device, or host
isolation claim. The final image build has no network access. Its
content-addressed archive and package records are retained inside the release
staging tar and replayed offline before qualification. They are not separate
public Release assets, and every applicable record states
`rebuildReproducibilityClaim:false`: the retained archive proves exactly what
ran, not that a future rebuild from rolling mirrors will reproduce the same
bytes.

The automated upgrade and rollback scenarios use a second isolated release
target containing the same exact qualified full-suite artifact and version.
They prove deployment transactions, target isolation, supervision, readiness
failure recovery, and cleanup; they do not prove compatibility between
different application versions. Cross-version migration compatibility requires
a separately defined test with an authenticated historical artifact.

## Protected staging and publication

Protected staging downloads the seven exact bundles and retained-runtime
snapshot from the Android run and the one exact twelve-member qualification
evidence artifact from the independently
discovered qualifier run, all by artifact ID with server-digest enforcement.
It does not accept a qualifier run ID, base64 evidence, or an
operator-selected qualification class.
The stage validates the automated envelope and every bound report from one
immutable snapshot, records the qualification class and negative claim
boundary in staging manifest v2, and preserves the fixed public set of sixteen
assets. The archive, package lock, snapshot, and replay stay inside the
unchanged staging tar and never expand the public asset count.

The existing `release-qualification`, `release-production`, and
`release-final` approvals remain mandatory. Publication still requires the
pre-created protected annotated tag, exact empty draft, immutable Releases
policy, no-bypass tag ruleset, two disjoint publication approvals, fresh draft
re-download verification, and final public byte verification. Automated
qualification removes only the manual physical-soak prerequisite; it does not
weaken administrator or publication controls.

The committed qualification inputs are
[`release-qualification-policy-v1.json`](release-qualification-policy-v1.json),
[`automated-native-deployment-scenarios-v1.json`](automated-native-deployment-scenarios-v1.json),
their closed
[`release-qualification-policy-schema-v1.json`](release-qualification-policy-schema-v1.json)
and
[`automated-native-deployment-scenarios-schema-v1.json`](automated-native-deployment-scenarios-schema-v1.json),
the current aggregate and specialized schemas, classifier v3, automated
envelope schema v1, and staging manifest schema v2. Historical aggregate,
specialized, classifier, staging, inheritance, runtime, and physical schemas remain
immutable for audit. They are not accepted as the automated qualification
class.
